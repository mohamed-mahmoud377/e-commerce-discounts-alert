# 2B Egypt (2b.com.eg): site analysis and how we crawl it

Everything we learned about 2b.com.eg (2B, an electronics and appliance chain) while adding it as the
fifth shop (27 October 2026). The adapter is `src/deals/sites/twob_eg.py` (site name `2b_eg`); its tests
are in `tests/test_parsers.py` (`test_2b_*`) against the saved API answer `tests/fixtures/2b_products.json.gz`
(TVs above 3,000 EGP). Sizes are from October 2026 and drift.

## Summary

| Question | Answer |
| --- | --- |
| Site name in the code and config | `2b_eg` (Arabic name in alerts: توبي (2B)) |
| Platform | Magento 2 (English store view `en`, Arabic is the default) |
| What we fetch | The shop's public **GraphQL API** (`POST https://2b.com.eg/graphql`, header `Store: en`): structured JSON, no HTML parsing |
| Products per request | 100 (`pageSize`; the API accepts 500 and more, 100 keeps answers small) |
| Deepest page | No cap (`max_slice_total` 2,000, so the planner splits anything bigger) |
| Exact count | Yes, `total_count` on every answer |
| Bot protection | Cloudflare. Chrome's TLS fingerprint passes from a home IP, HTML and GraphQL alike; plain `curl` also worked from the Mac |
| Who can crawl it | Home/office connections only. The droplet gets the "Just a moment..." challenge on `/graphql` too |
| How products are keyed | Magento's `sku` (e.g. `TV442`, `GM571`) |
| How categories are keyed | Magento's numeric category id (`category:131` = TVs), see "Why numeric ids" |
| How big categories are split | By price only, like every shop |
| Politeness | 1 to 2 s between requests per worker (`[sites.2b_eg]`); one request covers 100 products |
| Tracked | about 1,700 products across all groups at the group minimums (28 roots), all in stock |

## Access

The HTML pages and the GraphQL endpoint are behind Cloudflare. From the Mac both answer with Chrome's
fingerprint (and even plain `curl` with a browser User-Agent got the API); from the droplet everything is
challenged (HTTP 403, "Just a moment..."). On a challenge (403/429/503 or a non-JSON answer) the adapter
retries once with a fresh session, then raises `Blocked` and the coordinator pauses 2B for that IP.

`robots.txt` keeps search engines off filtered HTML pages (`?price=`, `?product_list_`); the API is not
mentioned. We send about one request per 100 products with a 1 to 2 s pause.

## The API

One POST per page, JSON body `{"query": "..."}`:

```graphql
{
  products(filter: {category_id: {eq: "131"}, price: {from: "3000", to: "10000"}},
           pageSize: 100, currentPage: 1, sort: {position: ASC}) {
    total_count
    page_info { current_page total_pages }
    items {
      sku name url_key url_suffix brand_name
      stock_status only_x_left_in_stock rating_summary review_count
      price_range { minimum_price { regular_price { value } final_price { value } } }
    }
  }
  category: categories(filters: {ids: {eq: "131"}}) { items { id name children { id name product_count } } }
}
```

Searches use `products(search: "playstation 5", filter: {price: {...}})`. The `category` part (only on
category slices) validates the id (`UnknownTarget` when it returns nothing) and gives `deals categories`
its children with their product counts.

**The price filter** is on the final (discounted) price and inclusive at both ends: `from: "11699", to:
"11699"` returns the two TVs at exactly 11,699; `from: "11699.5"` returns none. Decimals are accepted.
Prices on 2B are whole pounds.

**Only in-stock products are returned.** All 97 TVs answered `IN_STOCK`; the shop hides sold-out
products (Magento's "display out of stock products" is off), so a product that sells out disappears from
its category and is simply not seen until it is back (like Jumia). A product page still exists for it.

**Unknown ids and pages.** `category_id` 999999 returns `total_count` 0 with no error, hence the separate
category lookup. A page past the end returns an empty `items` list. Unknown HTML URLs redirect to a search
page, which is irrelevant to the adapter.

### Why numeric ids

A category's `url_path` in the API often differs from the path in the site's menu (Headphones is
`mobile-and-tablet/headphones` in the API but `/en/audio/headphones.html` in the menu; Televisions is
`home-appliances/large-home-appliances/tvs/televisions`), so a path copied from the browser would not
resolve. The numeric id is what every URL and the API agree on. `deals categories 2b_eg <id>` prints
children as `Name (count)  category:<id>`; the roots known to the command are Computer `118`, Mobile &
Tablet `266`, Home Appliances `2370`, Televisions `1932`, Audio `2382`, Gaming `120`, Electronics `610`.

## What a product contains

| Field | Example | Used as |
| --- | --- | --- |
| **`sku`** | `TV442` | `Listing.sku` |
| **`name`** | "Xiaomi TV 43 Inch LED FHD Smart - Google TV With Built In Receiver - L43MB-AFME (2026)" | title |
| **`url_key`** + **`url_suffix`** | `xiaomi-tv-43-inch-...-2026`, `.html` | `https://2b.com.eg/en/<url_key>.html` |
| **`price_range.minimum_price.final_price.value`** | 11699 | price |
| **`regular_price.value`** | 15999 (shown as "was EGP 15,999" on the site) | crossed-out price, kind `list` |
| **`stock_status`** | `IN_STOCK` | in stock |
| **`only_x_left_in_stock`** | 1 to 5, null on 43% | stock left. Present on 57% of TVs, so `2b_eg` is in `LOW_STOCK_EVERYWHERE` and it is not evidence |
| **`rating_summary`**, **`review_count`** | 100, 1 | rating (0-100 scaled to 0-5, None without reviews), reviews |
| **`brand_name`** | "Xiaomi" | brand |
| `categories` | TVs, Televisions, Bestseller, Offers, Ultra, "Hardware 12 months" | not used (Offers / Bestseller membership could become a badge) |
| `special_to_date`, `new_from_date` | null | not used |
| `is_installment`, `installment_plan` | false | not used |
| `labels`, `dynamic_labels`, `productLabel` | objects (need sub-selections) | not used yet; the HTML cards also show "N sold in the last week", which the API does not expose |

Every product carries a `regular_price` above its `final_price` (the site shows "Save EGP 4,300" on each
card: claims of 25 to 30% are the norm), so the crossed-out price is the shop's own claim, treated like an
RRP. New-listing alerts therefore rarely fire on 2B; its alerts come from our own price history.

## Performance and capacity

An API answer with 100 products is about 40 KB and takes about 0.5 s from the Mac. The 28 roots are 28
slices (none above 2,000 products); a full pass is about 35 requests, under two minutes of one worker.

## Running and checking it

```bash
.venv/bin/deals categories 2b_eg                    # known roots
.venv/bin/deals categories 2b_eg 2370               # Home Appliances: children with counts and ids
.venv/bin/deals crawl 2b_eg "category:131|price:3000-" --show 5
.venv/bin/deals crawl 2b_eg "search:playstation 5|price:8000-"
```

On the server, `make sql`:

```sql
SELECT grp, count(*) products, sum(in_stock) in_stock FROM products WHERE site = '2b_eg' GROUP BY grp;
SELECT kind, count(*), sum(failures > 0) failing, min(next_due_at) FROM jobs WHERE site = '2b_eg' GROUP BY kind;
```

## Troubleshooting

| Symptom | Meaning | Fix |
| --- | --- | --- |
| `blocked: 2b_eg: Cloudflare challenge` | Cloudflare refuses this connection | From home: `deals crawl 2b_eg "category:131\|price:3000-"` should print about 100 products; if every request is challenged try another `IMPERSONATE` target in `twob_eg.py`. From a cloud IP: expected, remove `2b_eg` from that worker |
| `UnknownTarget: 2b_eg: no category with id N` | Wrong id | `deals categories 2b_eg <parent id>` |
| `UnknownTarget: category ids are numbers` | A slug was put in the config | Use the numeric id |
| `ValueError: 2b_eg: GraphQL error ...` | The API rejected a field (Magento upgrade renamed it) | Check the message, adjust `PRODUCT_FIELDS`; save a fresh answer into `tests/fixtures/2b_products.json.gz` |
